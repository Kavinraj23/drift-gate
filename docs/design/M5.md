# M5 design note: investigator agent loop, orchestrator, offline end-to-end

## What was built

| Piece | Where |
| --- | --- |
| Investigator: tool-use loop against `ModelClient`, no framework | `agents/investigator.py` |
| Closed remediation catalog per tier | `remediation_catalog.py` |
| Orchestrator: pre-filter, investigator, deterministic gate facts, SafetyGate, target, audit; `build_synthetic_orchestrator` | `orchestrator.py` |
| Scripted model for each scenario family and the misbehaving variants | `eval/scripted_agent.py` |
| End-to-end runner and table (`fake`, `replay`, `auto`) | `eval/e2e.py`, `python tasks.py e2e` |
| Tests | `tests/agents/`, `tests/e2e/`, shared fixtures in `tests/conftest.py` |

### Investigator
Offers the seven read-only tools plus `submit_report`, a no-side-effect tool that carries the structured report out of the loop. A text-only response containing a JSON report is also accepted; a response with neither gets one nudge, then the run abstains.

Enforced in code, not by the prompt:
- **Tool-call budget.** `budget.consume_tool_call()` is called before every tool execution (unknown tool names included). A `False` return (the 9th call) abstains with `budget_truncated=true` and a partial evidence bundle built from the tool results actually returned, each cited by its real id. A test spies on the budget and proves one `consume` per call.
- **Token budget.** Checked before every model call and after every response (a response that blows the budget is not acted on). The gateway raises `InvestigationBudgetExhausted` itself; that is caught too. A client that does not log calls (the scripted fake) gets a `CallRecord` added by the loop, so `run` stats and the token limit work identically for fake and gateway.
- **Unique tool call ids.** A repeated or empty id is rejected: the call is not dispatched, costs no budget, gets an `is_error` tool result, and is counted (`duplicate_ids_rejected`).
- **Evidence integrity (invariant 7).** After the model reports, evidence is kept only if `source` is the id of a tool call of this run and the item is well formed. The number dropped is recorded. If nothing survives, the report abstains and the proposal is discarded (an uncited proposal never reaches the gate). A malformed report (bad enum, tier, confidence) abstains too.
- **Gateway failures** (spend cap, retries exhausted) abstain with "model unavailable" and escalate. `FixtureMissing` is a setup problem and propagates.
- Static, cache-friendly prefix: the system prompt and tool list are constants and identical on every request; the first user message is a pure function of the execution id. The request holds a copy of the message list, so recorded requests are not mutated by later turns.
- Confidence is stored on the report and in the audit; nothing in the loop or the orchestrator reads it for a decision.

### Orchestrator
`handle(execution_id)`: pre-filter closes governance and aborts with zero model calls (audit `rejected`, stage `prefilter`). Otherwise a fresh `InvestigationBudget`, the investigator, then:

1. **Gate facts are computed in code**, by calling `classify_signature`, `fleet_correlate` (always) and `flake_history` (Tier 0 only) directly, with ids `gate:<exec>:<tool>`. They do not depend on what the model called or claimed. The report's `fingerprint` and `blast_radius` are overwritten from these results, so `BlastRadius` is always populated explicitly and the model's values are never used.
2. Facts: `signature_match` = deterministic match; `known_transient_rule` = deterministic match AND the primary signature has a Tier 0 rule; `flake_precedent`; attempt history (`prior_tier0_failed` from the attempt store); `agent_confidence` (recorded only).
   Set sizes and shared resources by tier: Tier 0 touches the failed leaf steps out of all leaf steps; Tier 1 touches one resource on the dimension its action names (`refresh_connector_token` is a connector, pool actions a runner pool) out of the distinct values of that dimension; Tier 2 touches one lock out of the distinct infra definitions; Tier 3 touches `len(paths)` files, no total, and an empty path list is refused by the gate as an empty set. Tier 1/2 with unknown sizes fail closed in the gate.
3. A catalog and path check (`remediation_catalog.py`; Tier 3 paths must be relative and inside the repo) runs before the gate. It can only escalate.
4. `SafetyGate.decide`, audited with `record_decision`. Only `allowed` goes on.
5. Tier 0: `dry_run`, then `execute`, then an attempt is recorded (for `prior_tier0_failed` and M7). Tier 1/2: `dry_run` only, outcome `awaiting_approval` (approval is outside the MVP). Tier 3: no target call at all; outcome `pr_proposed` on branch `driftgate/<fingerprint>-<action>`, `merged=false` in the audit. Anything not allowed or failing is `escalated` with a reason copied to `report.escalation_reason`.
6. `report.run` is the budget rollup (`tool_calls` counts the agent's calls only; the orchestrator's own gate-fact calls are deterministic checks and not counted).

Audit trail per case: `proposal` (stage `agent`: action, tier, confidence, abstained, truncated, kept/dropped evidence, duplicate ids, call ids), optionally `budget_truncated`, `proposal` (stage `gate_facts`: the exact `GateFacts`), `gate_decision`, `execution` (stages `dry_run`, `execute`, `pr_proposed`), `failed`, and `rejected` (stages `prefilter`, `agent`, `facts`, `validation`, `gate`) for every escalation. A case with no proposal or an abstention ends in `rejected`.

Only `orchestrator.py` imports `SyntheticTarget` (a test scans `src/` and asserts exactly that); `agents/` and `tools/` import neither it nor the orchestrator.

**Extension points** (documented in the module docstring, empty in M5): `tier3_review(investigation, remediation) -> Review | None` (M6: `approve` lets the PR proposal stand, anything else escalates) and `after_execution(outcome)` (M7: verify the next execution and run the single re-investigation round; `Orchestrator.attempts` and `begin_reinvestigation()` are already there). Both are exercised by a stub in tests; no reviewer or verification logic exists.

### Scripted scenarios (`eval/scripted_agent.py`)
Reads the scenario label (allowed in `eval/`) to decide the correct diagnosis, emits real-looking sequences (ids `toolu_<exec>_<n>`, `get_execution` + `classify_signature` in the first turn, cheap tools before `get_step_logs` and `read_repo_file`) and a final `submit_report` built as a function of the real tool results in the conversation, so the findings describe what the tools returned. Families: flaky precedent, throttling and registry rate limit (Tier 0 rule), lockfile / provider pin / undefined variable / pip pin (Tier 3 with `read_repo_file` of the fix file), Tier 1 (expired token, OOM), Tier 2 (state lock; the gate refuses to trust it), fleet-wide (investigates, proposes nothing, escalates, as the prompt tells it to), unknown (escalates), governance (empty script: any model call fails). Variants: `bogus_evidence`, `all_bogus_evidence`, `duplicate_ids`, `budget_calls` (a 9th tool call), `budget_tokens`, `overconfident_tier0` (Tier 0 at 0.99 whatever the facts), `ignore_fleet` (proposes the fix despite a fleet).

### E2E (`eval/e2e.py`, `python tasks.py e2e`)
Each of the 33 scenarios (24 dev, 9 held-out) gets a fresh orchestrator, rate limiter, audit log, kill switch file and deterministic `StepClock`. Columns: scenario, set, fault, expected, actual, status, model source, model calls, tool calls, tokens. Exit code 0 when no row is a mismatch or missing a fixture. `tasks.py e2e` runs mode `auto`.

Expected vs actual: `remediate` labels expect `executed` (Tier 0) or `pr_proposed` (Tier 3) with the labelled action; `escalate` labels expect `escalated`, or `awaiting_approval` for Tier 1 platform cases (counted as human-required, noted in the table); `close` labels expect the pre-filter. **Known label conflict**: the three flaky-test scenarios are labelled Tier 0 via flake precedent, but their only signature is the bare exit code, so the gate (correctly, invariant 3) downgrades them. They are marked `known label conflict` with the real gate outcome and reason; the gate is not bent and the rows are not hidden. A row only gets that status if the label says `flake_precedent` AND the gate's reason is "no deterministic signature match"; any other deviation is a mismatch.

Result (seed 20260908, scripted model): 33 scenarios, 30 ok, 3 known label conflict, 0 mismatch; 109 model calls, 109 tool calls, 212,060 scripted tokens; governance rows 0 model calls. Outcomes: 5 Tier 0 executed, 9 Tier 3 PRs proposed, 2 Tier 1 awaiting approval, 2 closed by the pre-filter, 15 escalated with reasons (3 of them the known label conflict).

## Modes and replay keys
- `fake` (default in the module): scripted fake. `replay`: `Gateway(mode="replay")` over `fixtures/replay/`, no ledger, no key, no network; a scenario without fixtures reports `no fixture` and fails the run. `auto` (what `tasks.py e2e` uses): replay where the fixtures exist, otherwise the scripted fake, labelled `fake (no fixture)` in the source column and the table header says the table is mixed. There is no live mode and the module reads no environment or `.env`.
- A replay key is `sha256(canonical JSON of {model, max_tokens, system, tools, messages})`. The investigator builds the first request from constants (`SYSTEM_PROMPT`, `agent_tool_definitions()`, `max_tokens=1500`) and `initial_message(execution_id)`, so request 1 of a scenario is identical for the scripted fake, `record` and `replay`. Later requests contain the previous responses and the (deterministic, seeded-data) tool results, so a recorded run replays exactly as long as the code that builds requests is unchanged. A test records the scripted model through a recording wrapper (what `record` does with the real API) and proves replay reproduces the same outcome.
- Changing `SYSTEM_PROMPT`, a tool description or schema, `max_tokens`, the initial message, the seed, or the result format of any tool changes every key and invalidates all fixtures.

## How the human records fixtures (`record`, not implemented, human-only)
`record` should, per scenario that is not closed by the pre-filter (31 of 33): build `Gateway(load_config(), mode="record", fixtures=FixtureStore("fixtures/replay"))` (the key comes from `.env` via `load_config()` in the human's shell only), run `Orchestrator.handle(execution_id)` with `model_factory = lambda eid, budget: gateway.bind(budget)` (investigator model Haiku 4.5), and let the gateway save one fixture per request. Requirements: skip scenarios whose first fixture exists unless `--force`; run dev scenarios first and stop on `BudgetExceeded` (lifetime $2.50, daily $1.00 are enforced by the gateway); print the running spend; never write the key to the fixtures (they hold requests and responses only). Rough cost: the scripted run uses about 212k input+output tokens over 109 calls, so a real Haiku run should cost well under a dollar (check the price table first; M2 flagged the Sonnet entry as an estimate). Then `python tasks.py e2e` replays them with no key. The recorded model will not behave like the script (it may take other paths, propose other actions, or hit the Tier 0 gate), so expect real `MISMATCH` rows to analyse; that is the point.

## Open doubts
- **Ceiling N.** The orchestrator uses N = 2 so a 3-execution fleet escalates (BLOCKERS.md). The M4 default of 10 would let a fleet of 3 to 10 through the gate; the investigator's prompt is the only other thing stopping it.
- **Tier 2 can never execute**: no deterministic holder-liveness source reaches the orchestrator, so the gate downgrades all of it. Safe, but untested end to end beyond that.
- **Tier 1/2 outcome.** `awaiting_approval` has no approval flow; the e2e judge counts it as an escalation for `escalate` labels. If the human wants Tier 1 proposals to be escalations in the output, it is a one-line change in `_act`.
- **Scripted model is correct by construction.** The table proves the pipeline and the gates, not agent quality; real numbers need `record` and `eval`. The fleet cases script the agent to obey the prompt and propose nothing; the gate's fleet path is covered by the `ignore_fleet` variant.
- **Dry run happens after the gate**, so Tier 2's "mandatory dry-run before approval" fact (`dry_run_ok`) is always false at decision time. Irrelevant while Tier 2 is always downgraded; M6/M7 or a later Tier 2 effort has to reorder this.
- **Rate limit is per `RateLimiter` instance**; the e2e builds one per scenario. A long-running service must share one per process (M4 carry-forward).
- The rate limiter counts only allowed decisions, so downgraded or refused attempts do not consume the 2-per-hour allowance (M4 behaviour, unchanged).
- `rejected` is used for pre-filter closes and no-proposal escalations because the audit kinds have no "closed" or "escalated"; adding kinds belongs to the core owner.
- `evidence_dropped` is kept on the `Investigation` and in the audit, not in the Report (the contract has no field for it).
- The 8-call limit is checked by the loop; the gateway still enforces only tokens (M2 question 1 stays open).
