# M6 design note: Tier 3 code-change path and the PR reviewer agent

## What was built

| Piece | Where |
| --- | --- |
| Structured unified diffs: parse (files, hunks), strict apply, render | `diffs.py` |
| Deterministic Tier 3 pre-checks (`check_diff`), PR types, PR description, `ReviewerHook` | `tier3.py` |
| Independent reviewer agent (own prompt, `read_repo_file` only, `submit_review`) | `agents/reviewer.py` |
| Investigator proposal carries `diff` (additive field in `submit_report.remediation`) | `agents/investigator.py` |

| Tests | `tests/tier3/` (4 modules, 100+ cases) |

`tasks.py`: `M6` added to `IMPLEMENTED_MILESTONES`.

### The flow (per Tier 3 proposal that SafetyGate allowed)
1. `check_diff` (deterministic, before any model sees the diff). Any violation escalates (`rejected`, stage `diff_check`); it never edits the diff and never raises a tier.
2. The reviewer (`tier3_review` hook) returns approve / revise / reject. Recorded in `report.review` and an audit `proposal` entry (stage `tier3_review`, with round, verdict, comments).
3. `approve`: the PR record opens through the target. `reject`: escalate. `revise` (first time only): the comments plus the previous diff go to a fresh investigator run (same system prompt and tools; only the first user message is extended), the revised proposal goes through the same catalog/path validation, the gate (a second `gate_decision`), the diff checks and a second review. A second `revise` escalates ("revision limit reached"); there is no third review.
4. PR: `PullRequest(branch="driftgate/<fingerprint>-<action>", base="main", body=...)`. The body holds the hypothesis, the changed files, the whole evidence bundle (`source: finding`), and the reviewer's verdict and comments (plus the revision count). The record has `merged=False`; no code path can merge (the target has no merge method, and a test asserts none exists). The single `execution` audit entry (`stage=pr_proposed`) keeps its M5 fields and adds `pr_number`, `reviewer_verdict`, `revisions`.

### Deterministic diff checks (`tier3.check_diff`)
Violation codes: `no_diff`, `parse_error`, `rename`, `deletes_file`, `unsafe_path`, `protected_path` (`.env*`, keys/certs/tfstate, `credentials*`, `secrets/`, `kill_switch*`, `.git`, `.claude`, `.driftgate`; such files are not even read), `undeclared_path` (the diff may touch only files the proposal declared, which is also what the gate counted), `unrelated_path` (a per-action allow-list of file patterns, e.g. `regenerate_lockfile` may touch lockfiles/manifests, not workflows), `too_many_files` (3), `too_large` (60 changed lines), `secret_literal` (AWS key id, GitHub/provider tokens, private key blocks, `password = <literal>`; the audit stores the pattern name, never the text), `subtractive_before_additive` (invariant 13: a file that net-removes lines may not precede one that adds), `does_not_apply` (strict context match at the stated line or one unique offset; an unreadable or >200 KB base file counts as not verifiable), `no_op`.

### Reviewer isolation and limits
It receives a `ReviewRequest` (repo, ref, hypothesis, diff, target files' current contents, round). `ReviewerHook` builds it from `rem.dry_run` and `report.hypothesis`; the investigator's tool results, evidence, ids, confidence, classification and prompt are not passed (a test scans every reviewer request for them). Tools offered: `read_repo_file` and `submit_review`; any other tool name is refused and never dispatched. Budget: a small `BudgetView` of its own (3 tool calls) whose usage is also charged to the case's one shared `InvestigationBudget` (see M7.md, Case rules). Fail closed: malformed verdict, no verdict after one nudge, budget exhaustion or a gateway error all become `reject`. The reviewer's usage is added to `report.run` (tool calls, tokens, cost).

### Seeded bad diffs and who stops them
`wrong_file`, `over_broad` pass the deterministic checks by design (right action, declared, in scope, small) and are stopped only by the reviewer. `delete_fix_file`, `secret_literal`, `huge`, `subtractive_first` are stopped by the checks even when the reviewer would approve (tested with a `lenient` reviewer, which is never even asked). `unrelated_workflow` is stopped by the checks except for `fix_undefined_variable`, where workflows are in scope and the reviewer is the control. Tests also show the residual risk: a lenient reviewer lets `wrong_file` through.

### Tier 3 quality scoring (for M9a)
`eval/tier3_scripts.score_tier3(label, source, outcome, audit) -> Tier3Score` compares the SHA-256 of the files the proposed diff produces with those of the labelled fix (not diff text), and records whether a PR opened and which layer (validator / reviewer / gate / agent) stopped it. `tier3_quality(scores)` aggregates: correct-diff rate, correct diffs approved/rejected (false rejections), bad diffs caught/missed, catch rate.

## Decisions
- **Where the diff lives.** `remediation.diff` (string) in the `submit_report` tool; `Proposal.diff`; after parsing, `Remediation.dry_run["diff"]` (structured: files, hunks, counts) and `["diff_text"]`. `contracts/` is untouched (`dry_run` is a free object).
- **Prompt change.** `SYSTEM_PROMPT` gained one Tier 3 sentence (put the change in `diff`, minimal, additions before removals, no deletions, no credentials) and the tool schema gained `diff`. **Every replay fixture recorded before M6 is invalid** (none exist yet; M5 said the same for any prompt/tool change).
- **Reviewer wiring is opt-in in the orchestrator, always on in e2e.** With `tier3_review=None` the M5 behaviour stays (PR proposed, no diff checks, no review, no PR record), because existing M5 tests assert it and I could not weaken them. `eval/e2e.py` always wires the reviewer, so every Tier 3 case there is checked and reviewed. M8/M9 wiring of the live path must pass a `ReviewerHook` (open doubt 1).
- **Audit kinds unchanged.** `KINDS` is owned by core; review and diff events are `proposal` entries with stages `tier3_diff`, `tier3_review`, `tier3_revision`, escalations are `rejected` with stages `diff_check` / `review`.
- **Revision re-runs the investigator** rather than patching the conversation (on the case's shared budget, not a fresh one; prompt and tools identical). It is re-validated and re-gated, so it consumes one more allowed attempt of the 2-per-hour fingerprint rate limit (tested: a third attempt hard-escalates).
- **Ordering rule.** Whole-file deletion is always a violation, so "additive before subtractive" is enforced as: a file whose diff removes more lines than it adds must not precede a file that adds at least as much as it removes.
- **PR via an optional protocol.** `PullRequestTarget` (runtime-checkable) is separate from `RemediationTarget`, whose contract is unchanged; the GitHub adapter (M8a) implements `open_pull_request` too. No `RemediationTarget` implementation is imported under `agents/` or `tools/` (tests: M5's scan plus a new reviewer-specific one).
- **E2E replay mode.** The reviewer goes through `Gateway.bind(role="reviewer")` over the same fixtures; where reviewer exchanges were not recorded it falls back to the scripted reviewer and the column says `scripted reviewer`. This keeps the M5 replay test (investigator-only recording) valid unchanged.
- **Table `model calls`** counts the investigator only; the reviewer's usage is in `tool calls` and `tokens` (via `report.run`).

## Tested
`tests/tier3/` (run `python -m pytest -q tests/tier3`): diff parse/apply and offset/ambiguity handling; every labelled fix passes all checks; each check's violation code with unit cases (protected paths, traversal, rename, delete, caps, secrets without echoing, no-op, base too large, ordering both ways); every seeded kind against every applicable scenario stopped by the expected layer, with a strict and a lenient reviewer; reviewer isolation (no evidence, ids, tool output, investigator prompt in any request), only `read_repo_file` offered, other tools refused, verdict handling, malformed/absent verdicts, tool and token budgets, gateway failure; PR on a `driftgate/` branch, never merged, target refuses other branches; PR body holds evidence and verdict; audit ordering and content; reject/revise/second-revise/abstaining and rule-breaking revisions; rate limit counts the revision; kill switch stops before the reviewer; run stats include the reviewer; schema validity of the report; scoring, false-rejection and missed-bad-diff accounting; the e2e column and the replay fallback; architecture scans.

## Open doubts
1. **Reviewer is not mandatory in the orchestrator.** A caller that omits `tier3_review` gets the M5 path with no diff checks. The live path (M8) and eval (M9a) must wire `ReviewerHook`; consider making it required once M5's tests can be updated with a justification.
2. **The scripted reviewer is an oracle** (it compares with the labelled fix). It proves the plumbing and the deterministic checks, not that Haiku catches subtle bad diffs; `semantic` kinds are the real test and need `record`/`eval-live` (human-only). Recording must now include reviewer exchanges (`role="reviewer"`); otherwise replay uses the scripted reviewer for them.
3. **Lenient diff parsing.** Header counts are ignored and blank lines are context; real models often miscount. This is permissive about format but strict about content (every context and removed line must match), so it cannot weaken a check, but it may accept a diff `git apply` rejects.
4. **Allow-list per action is hand-written** (`ACTION_PATHS`). Real repos have other layouts (monorepos, `yarn.lock` in subdirectories are covered by name, `Pipfile.lock` etc.); `revert_template_bump` and `fix_secret_scope` have no seeded scenario (the one template-bump scenario is fleet-wide and escalates before Tier 3).
5. **Secret patterns are heuristics.** A real secret in an unusual format passes; the reviewer prompt and the protected-path list are the other layers.
6. **Revision cost.** A revision is a second investigation plus a second review, all inside the case's one 8-call / 40k-token budget (and at most one revision per case). The gateway's spend caps still apply.
7. **Merge with M7.** Both branches touch `orchestrator.py` (`Outcome`, imports, `_propose_pr` region) and `tasks.py` (`IMPLEMENTED_MILESTONES`). My edits are additive except that `_propose_pr` body was replaced; M7's `after_execution` is still called from `_after` at the end of the Tier 3 flow.
