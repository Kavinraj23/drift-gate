# M7: verification and re-investigation loop

## What was built

- `verify.py`
  - `Verifier`: after a remediation executes, calls `target.verify(...)` (the next execution of the same pipeline for Tier 0, the CI run on the PR branch for Tier 3) and checks whether the failure fingerprint recurred (the next execution's log is re-fingerprinted with the same signature and pipeline/step as the original). Verified: attempt marked `verified`, case closes; a green Tier 3 run is recorded as `remediation.dry_run["ci"] = {"status": "green", "note": "verified by CI"}`. Not verified: attempt marked `failed`, rolled back if the action is reversible, executed and the target supports `rollback`; the verification result (including a bounded excerpt of the next log) is stored on the `RemediationAttempt`, so `get_remediation_attempt` returns it.
  - `VerificationLoop`: the orchestrator's `after_execution` hook. Verified: stop. Not verified: at most one re-investigation (`budget.begin_reinvestigation()`); a failure in round 2, or any failure when the fingerprint already has an earlier failed attempt, hard-escalates with `Report.prior_attempts` filled (every attempt on the fingerprint, with round numbers; the first carries the hypothesis that led to it). `install_verification(orch)` wires it.
- `orchestrator.py` (additive): `Outcome` gains `attempt_id, rounds, verified, first_attempt_failed, earlier_model_calls, earlier_tool_call_ids`; `handle` is split into `_run_round`; `reinvestigate(first, context, precheck)` runs the second round; `attach_after_execution`, `target` / `analyzer` properties; `make_synthetic_target`; `build_synthetic_orchestrator(verification=False)`.
- `adapters/synthetic.py`: `SyntheticTarget(data_dir=...)` reads the dataset's follow-ups (only this adapter does). Tier 0 verify yields the recorded rerun status and, when it failed, the recorded log text; Tier 3 verify is "CI": green only if the proposed paths cover every file the correct fix touches. `SimulatedOutcome.verified=False` always forces "not verified". New `rollback()`.
- `tools/attempts.py`: `AttemptStore.update` and `all`.
- `eval/scripted_agent.py`: `wrong_paths` first-round variant; `build_reinvestigation_script` with modes `revise_escalate, right_paths, wrong_paths, repeat_tier0, same_hypothesis, no_read`; `two_round_factory`. The second-round hypothesis is built from what `get_remediation_attempt` returned.
- `eval/metrics.py`: `remediation_success_rate`, `recovery_rate` (and `recovery_text`) over `(label, outcome)` cases, for M9a.
- `eval/e2e.py`: rows show `rounds` and `recovery`; first_fix_fails scenarios run the two-round flow in fake mode; five drills (`run_all(..., drills=True)`, enabled by `python tasks.py e2e`) end with the headline metrics line.
- `tasks.py`: M7 added to `IMPLEMENTED_MILESTONES`.

## Decisions

- **The real gate stops the dataset's wrong first fix.** For `platform_throttle_masks_lock` the primary signature is the state lock (no Tier 0 rule, no flake precedent), so a Tier 0 re-run is downgraded before anything runs. sc-11 and sc-29 therefore escalate correctly in round 1 (recovery column "first fix blocked by gate"). To still exercise the loop end to end, drills d1/d2 use `NaiveClassifierOrchestrator`, a test double that makes the gate see a signature match and a known-transient rule (what the baseline's naive ranking would do). Production gate code is untouched.
- **Re-investigation context is in the user message only**, never in the system prompt or tools. Recorded fixtures of first-round requests keep their replay keys; only re-investigation requests (the second request of a two-round case) have new keys and need their own fixtures.
- **One budget for the whole case.** Round 2 shares round 1's `InvestigationBudget` object (tool calls, token usage, the single `begin_reinvestigation()`), so both rounds together stay within 8 tool calls and 40k tokens and round 2 gets only what round 1 left. If round 1 leaves too little, round 2 abstains with `budget_truncated=true` and the case escalates with the failed attempt attached. `report.run` is read from that shared budget (nothing is summed, so nothing double counts). Round-1 evidence is kept, then round-2 evidence is appended. Round 1 is not silently overwritten: `Outcome.earlier_tool_results` / `earlier_tool_call_ids` hold its tool results and ids (evidence integrity, invariant 7, is checkable across both), `Outcome.first_round` is a snapshot of the round-1 outcome, and `attempt_id` keeps the last real attempt id when round 2 escalates before executing.
- **Deterministic checks on the second round** (`precheck`): a proposal is refused if the investigator never read the failed attempt through `get_remediation_attempt`, or if the hypothesis is textually unchanged. This is the code-level version of "must explain why the first hypothesis was wrong"; it cannot judge the quality of the explanation.
- **Re-proposals go through the same gate** (shared rate limiter, kill switch re-read, abort ceiling); `prior_tier0_failed` makes a repeated Tier 0 ineligible (it was already in `_gate_facts`; the verifier now sets the attempt's `verified=False` that feeds it).
- **Audit** uses the existing kinds: `verification` with stages `result`, `rollback`, `closed`; `proposal` stage `reinvestigation_start`; `rejected` stage `verification_escalation` (and the existing per-stage escalations). No new kinds, so the audit-kinds test is unchanged.
- **Opt-in wiring**: `build_synthetic_orchestrator(verification=True)`. Default off so the M5 tests that assert exact target calls are unchanged; `eval/e2e.py` turns it on.
- Rollback is the optional `RollbackCapable` protocol in `verify.py` (the `RemediationTarget` contract is unchanged). A target without it gets an explicit "rollback unavailable" audit entry. Rollback consults the kill switch read-only (`SafetyGate.kill_switch`): if tripped it is skipped, audited (`skipped_by_kill_switch`), recorded on the attempt, and the case hard-escalates instead of re-investigating. A Tier 3 PR is never merged, so there is nothing to roll back.
- **Recovery rate follows the PRD**: only a verified fix after a failed first attempt counts. `recovery_breakdown` reports verified fixes, correct escalations after an attempt, not recovered, and wrong first fixes the gate stopped before they ran, as separate figures; `tasks.py e2e` prints all of them. The looser figure survives as `recovery_or_correct_escalation_rate`.

## Tested (`tests/verify/test_verify.py`, 31 tests)

Verified closes (Tier 0 and green CI "verified by CI"); unverified marks failed and rolls back when reversible, not when irreversible; red CI triggers re-investigation; attempt readable via `get_remediation_attempt` including the masked lock-error log and `recurred=True`; context only in the user message (system prompt and tools identical); only one round; second failure escalates with both attempts, revised hypothesis, original evidence, citations all real; Tier 0 retry failure and "earlier failed attempt" hard-escalate; precheck refusals; rate limit (exhausted, and expiring on the fake clock), kill switch flipped between rounds, and abort ceiling all bind the re-proposal; shared budget (two rounds never exceed 8 tool calls / 40k tokens; round 1 spending all 8 truncates round 2 and escalates; run rollup equals the shared budget); round-1 data retained; rollback unavailable and kill-switch-skipped rollback; audit order and completeness; every two-round report validates against `contracts/report.schema.json`; Tier 1 awaiting approval is not verified; verification is off unless requested; drills all end correctly; headline metrics (fake table: verified-fix recovery 1/5, correct escalation 2/5, not recovered 2/5).

## Open doubts

1. The fake table's verified-fix recovery is low (1/5) because four of the five drills are designed to end in escalation; the figure measures the drills, not a model.
2. Because the budget is shared, a round 1 that spends most of the 8 tool calls leaves round 2 unable to investigate; that case escalates (by design), but it may cost recoveries with a real model. The scripted drills fit (at most 7 tool calls in total).
3. Replay fixtures for a two-round case must record round 2 against the shared budget; the request content does not include budget state, so replay keys are unaffected.
4. Tier 3 CI is simulated from paths only (the proposal carries no diff), so "green" means "touched the right files". M8a/M8b replace it with a real CI run.
5. The in-place merge in `VerificationLoop` mutates the first `Outcome` into the final one; callers holding the round-1 report object see the round-2 report. Fine for `handle()`, but worth knowing for M6/M9a.
6. `NaiveClassifierOrchestrator` swaps `__class__` on a built orchestrator. It is test-double code in `eval/`, but it overrides a private method; if `_gate_facts` is renamed the drills break loudly.
7. The recurrence check re-fingerprints the next log with the same step name as the original; if a real next execution fails in a different step, `recurred` is computed against the original step and may be a false negative (the attempt is still "not verified" because the status is failed).

## Test changes on review (justification, per the no-weakening rule)

- `test_budget_rolls_up_across_both_rounds` and `test_each_round_gets_its_own_tool_call_and_token_allowance` asserted the old per-round budgets (sum of two budgets; budgets are distinct objects). The budget rule now binds the whole case, so those assertions were replaced by stricter ones: one shared budget, run rollup equals it, never more than 8 tool calls / 40k tokens, and round-2 truncation when round 1 spends everything.
- `test_headline_metrics_are_computed_from_the_cases` asserted `recovery_rate == 3/5`. `recovery_rate` now follows the PRD (verified fixes only, 1/5); the old figure is asserted under its explicit name `recovery_or_correct_escalation_rate` (3/5) and the breakdown is asserted too.

- **Order**: gate, then diff checks, then reviewer (and its one revision), then PR opened, then CI verification, then (on red CI) one re-investigation. Audit stage names are unchanged on both sides (`tier3_review`, `pr_proposed`, `verification` result/closed, `reinvestigation_start`, `verification_escalation`).

M7's scripted `wrong_paths` (round 1 and re-investigation) now proposes M6's seeded `wrong_file` diff (a file the action may change but which does not hold the fault), and `right_paths` proposes the label's `fix_diff`. The drills test the CI loop, not the reviewer. Real wrong-file diffs are still caught by `strict` in the normal Tier 3 scenarios (M6 tests unchanged).

## Case rules (shared budget, one revision)

- One `InvestigationBudget` per case. Round 1, a Tier 3 revision, the reviewer (every review) and round 2 all use it, so the whole case is capped at 8 tool calls and 40k tokens and `begin_reinvestigation()` is called once. `report.run` is always read from it (nothing is summed). A revision or round that starts with the budget already spent builds no model, abstains with `budget_truncated=true` and escalates (fail closed); a round 2 in that state keeps the failed attempt in `prior_attempts`.
- The reviewer gets a `BudgetView` (`llm/budget.py`): its own small limits (3 tool calls, `REVIEW_MAX_TOOL_CALLS`) bound its loop, and every tool call and model call it makes is also charged to the shared budget, which can stop it (token or tool-call exhaustion). If the shared token allowance is spent before a review, the reviewer is never called and the verdict is `reject` (`budget_tokens`). Its own `ReviewResult.budget` is the view (its own usage), the totals live on the shared budget.
- At most one revision per case. `Outcome.revisions` is carried from the round-1 outcome into the round-2 outcome and is not reset, so after a round-1 revision a `revise` verdict in round 2 escalates ("revision limit reached"), and a second `revise` ever escalates. Note the 2-per-hour fingerprint rate limit already counts the revision's gate decision, so in practice a round 2 after a revision is rate limited unless an hour has passed; the test moves the fake clock to reach the round-2 reviewer.

Test changes forced by the shared budget (justification, per the no-weakening rule):

- `test_reviewer_usage_is_rolled_into_the_run_stats` (tier3) asserted `report.run.tool_calls == inv.budget.tool_calls + reviewer_calls`, which presumed separate budgets. The reviewer is now on the investigator's budget, so the assertion is `run == shared totals == investigator tool results + reviewer calls`, plus token totals equal to the shared budget and at least the reviewer's own tokens.
- `test_e2e_seeded_bad_diff_shows_as_a_stopped_pr_and_a_mismatch` asserted `model_calls == 4`. The scripted Tier 3 investigator now makes 3 tool calls instead of 4 (`get_step_logs` dropped), so a revision plus two reviews fit in 8 calls; its model turns are 3.
- `test_consume_tool_call_is_called_once_per_tool_call` (agents) asserted 4 tool calls for the scripted Tier 3 lockfile case; the script is now 3 calls (same reason: a revision and two reviews must fit in 8). The property under test, one `consume_tool_call` per executed call, is unchanged.
- Scripts shortened (no assertion changed): the Tier 3 plan in `scripted_agent._plan` is `get_execution`+`classify_signature`, then `read_repo_file`; the scripted re-investigation drops its `get_execution` call (round 1 already read it). Worst scripted case (drill d3) uses exactly 8.

Doubt: a case with a revision plus a verification failure can run out of budget before round 2 starts, so a real model may escalate such cases instead of recovering them. That is the price of a hard per-case cap.
