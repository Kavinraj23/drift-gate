# M7: verification and re-investigation loop

## What was built

- `verify.py`
  - `Verifier`: after a remediation executes, calls `target.verify(...)` (the next execution of the same pipeline for Tier 0, the CI run on the PR branch for Tier 3) and checks whether the failure fingerprint recurred (the next execution's log is re-fingerprinted with the same signature and pipeline/step as the original). Verified: attempt marked `verified`, case closes; a green Tier 3 run is recorded as `remediation.dry_run["ci"] = {"status": "green", "note": "verified by CI"}`. Not verified: attempt marked `failed`, rolled back if the action is reversible, executed and the target supports `rollback`; the verification result (including a bounded excerpt of the next log) is stored on the `RemediationAttempt`, so `get_remediation_attempt` returns it.
  - `VerificationLoop`: the orchestrator's `after_execution` hook. Verified: stop. Not verified: at most one re-investigation (`budget.begin_reinvestigation()`); a failure in round 2, or any failure when the fingerprint already has an earlier failed attempt, hard-escalates with `Report.prior_attempts` filled (every attempt on the fingerprint, with round numbers; the first carries the hypothesis that led to it). `install_verification(orch)` wires it.
- `orchestrator.py` (additive): `Outcome` gains `attempt_id, rounds, verified, first_attempt_failed, earlier_model_calls, earlier_tool_call_ids`; `handle` is split into `_run_round`; `reinvestigate(first, context, precheck)` runs the second round; `attach_after_execution`, `target` / `analyzer` properties; `make_synthetic_target`; `build_synthetic_orchestrator(verification=False)`.
- `adapters/synthetic.py`: `SyntheticTarget(data_dir=...)` reads the dataset's follow-ups (only this adapter does). Tier 0 verify yields the recorded rerun status and, when it failed, the recorded log text; Tier 3 verify is "CI": green only if the proposed paths cover every file the correct fix touches. `SimulatedOutcome.verified=False` always forces "not verified". New `rollback()`.
- `tools/attempts.py`: `AttemptStore.update` and `all`.
- `eval/scripted_agent.py`: `wrong_paths` first-round variant; `build_reinvestigation_script` with modes `revise_escalate, right_paths, wrong_paths, repeat_tier0, same_hypothesis, no_read`; `two_round_factory`. The second-round hypothesis is built from what `get_remediation_attempt` returned.
- `eval/metrics.py`: `remediation_success_rate`, `recovery_rate` (and `recovery_text`) over `(label, outcome)` cases, for M9a.
- `eval/e2e.py`: rows show `rounds` and `recovery`; first_fix_fails scenarios run the two-round flow in fake mode; five drills (`run_all(..., drills=True)`, enabled by `python tasks.py e2e`) end with the headline metrics line.
- `tasks.py`: M7 added to `IMPLEMENTED_MILESTONES`.

## Decisions

- **The real gate stops the dataset's wrong first fix.** For `platform_throttle_masks_lock` the primary signature is the state lock (no Tier 0 rule, no flake precedent), so a Tier 0 re-run is downgraded before anything runs. sc-11 and sc-29 therefore escalate correctly in round 1 (recovery column "first fix blocked by gate"). To still exercise the loop end to end, drills d1/d2 use `NaiveClassifierOrchestrator`, a test double that makes the gate see a signature match and a known-transient rule (what the baseline's naive ranking would do). Production gate code is untouched.
- **Re-investigation context is in the user message only**, never in the system prompt or tools. Recorded fixtures of first-round requests keep their replay keys; only re-investigation requests (the second request of a two-round case) have new keys and need their own fixtures.
- **Each round has its own budget** (8 tool calls, 40k tokens); the second budget carries the `reinvestigations` count, so a third round cannot start. `report.run` is the sum of both. Round-1 evidence is kept, then round-2 evidence is appended; tool call ids of round 1 are in `Outcome.earlier_tool_call_ids` so evidence integrity (invariant 7) can be checked across both.
- **Deterministic checks on the second round** (`precheck`): a proposal is refused if the investigator never read the failed attempt through `get_remediation_attempt`, or if the hypothesis is textually unchanged. This is the code-level version of "must explain why the first hypothesis was wrong"; it cannot judge the quality of the explanation.
- **Re-proposals go through the same gate** (shared rate limiter, kill switch re-read, abort ceiling); `prior_tier0_failed` makes a repeated Tier 0 ineligible (it was already in `_gate_facts`; the verifier now sets the attempt's `verified=False` that feeds it).
- **Audit** uses the existing kinds: `verification` with stages `result`, `rollback`, `closed`; `proposal` stage `reinvestigation_start`; `rejected` stage `verification_escalation` (and the existing per-stage escalations). No new kinds, so the audit-kinds test is unchanged.
- **Opt-in wiring**: `build_synthetic_orchestrator(verification=True)`. Default off so the M5 tests that assert exact target calls are unchanged; `eval/e2e.py` turns it on.
- Rollback goes through an optional `rollback` method on the target (the `RemediationTarget` protocol is unchanged). A Tier 3 PR is never merged, so there is nothing to roll back.

## Tested (`tests/verify/test_verify.py`, 31 tests)

Verified closes (Tier 0 and green CI "verified by CI"); unverified marks failed and rolls back when reversible, not when irreversible; red CI triggers re-investigation; attempt readable via `get_remediation_attempt` including the masked lock-error log and `recurred=True`; context only in the user message (system prompt and tools identical); only one round; second failure escalates with both attempts, revised hypothesis, original evidence, citations all real; Tier 0 retry failure and "earlier failed attempt" hard-escalate; precheck refusals; rate limit (exhausted, and expiring on the fake clock), kill switch flipped between rounds, and abort ceiling all bind the re-proposal; budget rollup; audit order and completeness; every two-round report validates against `contracts/report.schema.json`; Tier 1 awaiting approval is not verified; verification is off unless requested; drills all end correctly; headline metrics (recovery 3/5 in the fake table).

## Open doubts

1. `recovery_rate` counts a correct escalation as a recovery when the label says escalate. The PRD says "did re-investigation fix it"; for a failure DriftGate may not fix, escalating correctly is the only good outcome, but a reader may want the two split (the `recovery` column does split them).
2. Rollback is not a gate decision, so the kill switch is not consulted before it. It only undoes an allowed action; if a human wants rollback to honour the kill switch, it is one check in `Verifier._roll_back`.
3. Per-round budgets mean a two-round case may use up to 16 tool calls and 80k tokens in total. The PRD's "per-investigation" is ambiguous on this; a shared budget would leave round 2 with whatever round 1 did not use.
4. Tier 3 CI is simulated from paths only (the proposal carries no diff), so "green" means "touched the right files". M8a/M8b replace it with a real CI run.
5. The in-place merge in `VerificationLoop` mutates the first `Outcome` into the final one; callers holding the round-1 report object see the round-2 report. Fine for `handle()`, but worth knowing for M6/M9a.
6. `NaiveClassifierOrchestrator` swaps `__class__` on a built orchestrator. It is test-double code in `eval/`, but it overrides a private method; if `_gate_facts` is renamed the drills break loudly.
7. The recurrence check re-fingerprints the next log with the same step name as the original; if a real next execution fails in a different step, `recurred` is computed against the original step and may be a false negative (the attempt is still "not verified" because the status is failed).
