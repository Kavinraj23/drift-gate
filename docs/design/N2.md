# N2: `similar_history` retrieval (offline half)

Status: the tool, the index, the leakage tests and the offline on/off comparison are built. The milestone is **not
done**: the PRD's question (does retrieval help a real model?) needs recorded real-model on/off fixtures, which do not
exist and are human-only (`record`, `eval-live`). N2 is not ticked in TASKS.md.

## What was built
- `src/driftgate/retrieval.py`: `HistoryIndex`, a SQLite FTS5 table (stdlib `sqlite3`) plus a plain meta table holding
  `execution_id` and `finished_at`. `fts5_available()` is checked at construction and `FTS5Unavailable` is raised with a
  clear message otherwise. `query(text, as_of, case_id)` returns the top 3 by `bm25()`. `match_query()` turns log text into
  safe FTS5 syntax.
- `src/driftgate/tools/similar_history.py`: the read-only tool. It takes NO arguments (the schema is an empty object
  with `additionalProperties: false`, so any argument is rejected). The case id and its start time come from
  `ToolContext.bound_case`, which `Investigator.investigate` sets in code (`ctx.bind_case(execution_id)`, start read
  from the source) at the start of every investigation, so round 2 and every re-run are bound too. An unbound context
  (the reviewer's, any direct `dispatch`) makes the tool refuse with ok=False (fail closed). The query is derived in
  code from the case's own signature id, failed step name and top error block, and the output is redacted again. The result carries the caller's tool call id
  like every tool, so evidence can cite it (invariant 7 is exercised in a test).
- `Orchestrator.record_incident(outcome, completed_at)` writes a finished incident into the index. It is the only writer
  (a static test checks this). Stored fields: signature, fingerprint, key error excerpt, hypothesis, action taken
  (`a then b` when two rounds attempted different actions, `none` otherwise) and the verification outcome (`verified`,
  `not_verified`, `escalated`, `escalated_after_failed_attempt`, `pr_proposed_unverified`, ...), all from the report and
  the verification loop, never from a label.
- Optional and off by default: `tools.OPTIONAL_TOOLS` is separate from `TOOLS`; `Investigator(optional_tools=...)`
  and `Orchestrator(history=..., offer_similar_history=True)` opt a run in. Both are needed: an index alone does not offer
  the tool. With it off, the tool list and the system prompt are byte-identical to MVP 1.
- `python tasks.py eval-retrieval` -> `src/driftgate/eval/retrieval_eval.py`: scripted-model on/off over the 33 labelled
  scenarios, time-ordered, writes `data/eval/retrieval.md` and `.json`. Includes `shipping_verdict`, the PRD's rule as a
  pure function.
- `e2e.run_scenario` and the helper below it gained two optional keyword arguments (`history`,
  `offer_similar_history`), default off.

## Why these choices
- **No leakage is enforced in SQL**, not in Python after the fact: `finished_at < :as_of AND execution_id <> :case_id`
  is part of the query that ranks results, so the top-3 cap cannot be filled by future rows and then trimmed. `as_of` is
  the case's start; an incident that finished at exactly the start is excluded (strictly before). The model cannot change
  `as_of`, the case id or the query text: the tool has no arguments and both values come from the bound case.
  - Round 2 fix: round 1 took `execution_id` from the model, so a model could pass a later execution's id (seeing
    incidents that finished after the real case started) or another earlier id (so the real case was not excluded).
    Now nothing the model sends can name a case. Tests: later id, earlier id, the real id, no bound case, and a bound
    case already in the index; all in `tests/retrieval/test_tool.py`.
- **FTS5 injection**: log text is reduced to distinct lowercase alphanumeric terms of 3 to 40 characters (max 32), each
  double-quoted and joined with ` OR `. No operator, column filter, prefix star, NEAR, parenthesis or quote survives.
  Words like `AND`/`NEAR` are quoted so they are plain terms.
- **Live incident time**: `record_incident(outcome, completed_at)` takes the time the incident COMPLETED (report,
  remediation and verification all finished). The index is therefore as-of completion, which is the conservative
  choice: a case that starts while an earlier incident is still being worked cannot see it. No latency is invented
  anywhere.
- **Incident finish time** for the synthetic eval is the failed execution's `finished_at` (when the pipeline run ended),
  not the time the agent finished. It is earlier than the agent's own completion, so it errs towards including an
  incident slightly early for later cases whose start falls in between. See doubts.
- **Index inputs are redacted and clipped** (600 chars per field) on insert, and again on output.
- **Prompt**: when the tool is on, `system_prompt()` appends one paragraph saying matches are leads, never satisfy a
  Tier 0 condition, must still be cited and cost one of the 8 calls. Off: no change. Prompt-cache layout is unchanged
  for the off case.
- **Budget**: no limit was changed. The call counts against the existing 8 (tested: a ninth `similar_history` call is
  refused and the run abstains with `budget_truncated`).
- **Eval honesty**: the scripted model never decides anything. The "on" arm adds one scripted `similar_history` call to
  the first turn (`HistoryProbe`) so that index, filter, budget, citation and redaction are exercised. The report says
  so in its first paragraph, shows counts beside percentages, prints no claim of improvement, and its verdict is
  computed by `shipping_verdict(..., recorded=False)`, which is always "stays off: no recorded evidence".

## What was tested (`tests/retrieval/`)
- Index: BM25 ordering and top 3, empty and symbol-only queries, redaction and clipping, replace on re-add, on-disk
  persistence, missing-FTS5 error.
- Leakage: before / long-before / equal / after / far-after / the case itself in one index; thirteen query strings
  including FTS5 operators, column filters, `NEAR`, prefix stars, quote injection and a NUL byte; asserts only strictly
  earlier non-self ids are returned. A boundary test at one millisecond. The schema has no label-like column.
- Tool: call id echoed, the query comes from the case, extra arguments rejected, not-enabled means not runnable,
  redacted output, nine calls hit the budget, uncited evidence is dropped.
- Off by default: sha256 snapshots of the MVP 1 tool definitions and system prompt, the MVP 1 prompt fingerprint
  (`88a8278480e61498`), the replay manifest's fingerprint equals the current one, requests sent by the orchestrator are the
  MVP 1 bytes by default and when only an index is given, and differ only when the tool is offered.
- Architecture: the two modules name no labelled data, import no eval/generator/adapters/SDK/network module; only the
  orchestrator writes the index.
- Eval: the 33-scenario comparison runs with zero leak violations and zero failed calls, off arm has 0 false remediations,
  on arm has no more, report says SCRIPTED and carries the `stays off` verdict.

## Result of the offline run (scripted model)
Both arms: recall 14/14, success 14/14, false remediation 0/33, escalation precision 19/19, same mean cost. 31/33
investigations called the tool, 30 of those returned at least one earlier (scripted) incident, 0 leak violations. This is
a plumbing result only.

## Open doubts
- The retrieval question itself is unanswered; it needs `record` fixtures with the tool on and off, then `eval-retrieval`
  re-pointed at them (the function takes `recorded=True` for that case, but the loader for recorded arms is not built).
- On the synthetic set, the index can only contain the 33 scenario incidents, scripted. Real BM25 quality (paraphrases,
  noisy excerpts) is untested; PRD says to add embeddings only if BM25 misses paraphrases.
- `shipping_verdict` thresholds (3 cases, 10 percent cost) are my reading of "do not claim one or two cases"; see BLOCKERS.md.
- Excerpt = top-ranked error block only, clipped at 600 characters. A multi-block failure may lose its operative cause.
- Replay fixtures are keyed on the full request, so an "on" run needs fresh recordings (the tool list and prompt differ);
  the "off" recordings stay valid.
