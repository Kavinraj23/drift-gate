# N3: Change correlation (`changes_in_window`, offline half)

Status: the tool, its per-run switch and the scoring are built and tested offline. The milestone is **not ticked**:
recording fixtures with the tool enabled and any live eval are human-only (`record`, `eval-live`), and until then no
real model has ever used the tool.

## What was built
- `src/driftgate/tools/changes_in_window.py`: read-only tool. Input `execution_id` and optional `window_minutes`
  (default 360, 1..4320). Returns every change in the window before the case's FIRST failure, nearest first, capped at
  25, with `total_in_window` and `truncated`. Fields per change: `change_id, at, kind, ref, actor, message, files, sha`
  (a code whitelist) plus `minutes_before_failure`. Message and file names pass through `redaction.redact`.
- Registry: `tools/__init__.py` gains `OPTIONAL_TOOLS` (not in `TOOLS`) and `optional_tool_definitions`; `dispatch`
  takes an `enabled` set and treats a non-enabled optional tool as an unknown tool, so a model cannot call it by name.
- Per-run switch: `Investigator(..., optional_tools=frozenset({"changes_in_window"}))`, passed through
  `Orchestrator(optional_tools=...)` and `build_synthetic_orchestrator(optional_tools=...)`. Default: empty = MVP 1.
  When enabled, the tool definition goes before `submit_report` and `system_prompt()` appends a short addendum.
- `src/driftgate/eval/change_score.py` and a labelled section in the offline report (`eval/report.py`).

## Decisions
- **First failure anchor.** The failure episode of an execution: walk back through the same pipeline's earlier
  executions while they are failed with the same fingerprint (a success, another status or another fingerprint ends the
  episode); the earliest one is the anchor. The window is `[anchor - window, anchor)`; the source's inclusive window is
  filtered again so nothing at or after the anchor is returned. Reason: a retried or recurring failure should not slide
  the window forward past the cause. Lookback is bounded at 50 executions.
- **Decoys are not filtered.** The tool never knows or ranks relevance; the description says a listed change is not
  evidence. The generator already puts causal and decoy markers only in `ground_truth/labels.json`; `changes.json`
  keys are exactly the eight whitelisted ones (a test pins that on the generated dataset). No generator change needed.
- **Source access, additive.** `ExecutionSource` (domain.py) is unchanged. A separate `ChangeSource` protocol
  (`list_changes(window)`) lives in the tool module; `SyntheticSource.list_changes` already existed. A source without it
  yields a clean `ok=False` tool error. If the PRD protocol is ever extended, `list_changes` is the additive candidate.
- **Byte-identical when off.** `agent_tool_definitions()` and `SYSTEM_PROMPT` are untouched on the default path;
  tests pin the prompt fingerprint (`88a8278480e61498`, computed on `mvp2/n1-holdout` before this change), the tool name
  list and the system prompt. Enabling the tool changes the request, so fixtures recorded with it on are a separate set.
- **Budget.** The call counts as one of the 8 tool calls; no limit was touched (a test asserts it).
- **Scoring** (`eval/change_score.py`, agent column only; baseline cell says it names no change):
  - suspected-change accuracy = reports whose `suspected_change` resolves to a labelled causal change / cases whose
    label has a causal change. No suspected_change is a miss.
  - decoy blame rate = reports that resolve to a labelled decoy (and not causal) / reports that named any
    suspected_change. Naming an unresolvable or unlabelled change counts in the denominator only; that count is printed.
  - Resolution: `ref` equal to a `change_id`, else a commit `sha` or a prefix of 7+ characters, else exact
    `(kind, ref, at)`. The tool and prompt tell the model to cite the `change_id`.
  - `n/a (n=0)` when no case applies. Counts sit beside percentages (the existing `fmt`).
- **Report placement.** A separate "Change correlation (N3, additional rows)" table after the MVP 1 metrics table, plus
  a `change_correlation` key in `report.json`. The MVP 1 table, the README-synced block and every existing metric are
  unchanged, so the frozen MVP 1 numbers still match. No existing test assertion was changed.

## What was tested (`tests/changes/`, offline, no sleep, no clock reads)
Boundary (strictly before; window start inclusive; configurable and validated), episode anchoring, decoys listed,
ordering with ties, cap, redaction, field whitelist even if the source adds `is_causal`, generated `changes.json` has
no causal/decoy marker, real-data output never at/after the failure and lists both causal and decoy changes, off-by-
default byte identity and fingerprint, a disabled tool cannot be dispatched, the call counts against the budget, scoring
math including zero denominators and a change that is both causal and decoy, and the report section.

## Open doubts
- With the scripted model or MVP 1 replay fixtures nothing names a change, so offline accuracy reads 0/N and blame
  `n/a (n=0)`. These validate the metric code only; real numbers need `record` with the tool enabled.
- The scripted model and `e2e` were not given the tool (it would add scripted behaviour the PRD does not call for).
- The generator makes cause commits at most 90 minutes before the failure and decoys 15..90 minutes before; the
  6-hour default window therefore contains both for every labelled case, which is the intended difficulty but also means
  the default window is generous. A recorded run will show whether the agent over-trusts proximity.
- The window is anchored on the pipeline's own failure episode. A fleet burst's cause (a template bump) predates every
  member's first failure, so it is found; a cause that predates the first failure by more than the window is not.
