# N4: Tier 1/2 with persisted CLI approvals

Branch `mvp2/n4-approvals`. Tier 1 and Tier 2 actions stay stubbed: the only target is the synthetic one, nothing runs against live infrastructure, and the GitHub adapter gained nothing.

## What was built

- `approvals.py`: the SQLite store (stdlib `sqlite3`) at `state/approvals.sqlite` (outside `data/`, which `tasks.py data` regenerates; `state/` is gitignored; the path and the clock are injected). Tables `requests` (id, execution_id, fingerprint, tier, action, requested_by, requested_at, expires_at, status, required, payload, note, gate_seq) and `decisions` (request_id, approver, decision approve|deny, at). Statuses: `pending -> approved | denied | expired | cancelled`, `approved -> executed | expired | cancelled`; the rest are terminal.
  - Tier 1: one approval, 15 minutes (`TIER1_TIMEOUT_S`). Tier 2: two approvals from two different people. A request is expired when `now >= expires_at`, so an approval at exactly 15:00 is refused; one at 14:59.999 is accepted. Expiry covers `approved` requests that were not executed in time, so an approval does not outlive its window.
  - Rules enforced in code AND in SQLite: `UNIQUE(request_id, approver)`; a trigger refuses an approval by the person who triggered the run; a trigger refuses decisions on a request that is not pending; a trigger allows only forward status transitions; decisions are append-only. Any denial ends the request (fail closed).
  - Round 2 (quorum and status): the quorum is always `REQUIRED_APPROVALS[tier]` computed from the immutable tier; the stored `required` column is never read for a decision (and is CHECK-pinned to the tier). tier, action, execution id, requester, `fingerprint`, `requested_at`, `expires_at` and `required` are frozen by triggers; `expires_at` is CHECK-bounded to at most 60 minutes after `requested_at`. A request can only be INSERTed `pending`; a trigger lets it become `approved` or `executed` only when the decisions table holds the tier's quorum of distinct non-requester approvals and no denial. I chose triggers plus a re-count in code at claim time over a derived status: the status column stays the single, simple thing the rest of the code reads, while SQL independently refuses any write whose decisions do not justify it. (Not claimed: this does not stop someone who drops the triggers from the file; execution's fresh gate is the real defence.)
  - Identities (round 2): an identity containing control, format (Cf), zero-width, line/paragraph separator or variation-selector characters is REFUSED (not stripped), then NFKC + case-fold + collapsed spaces, and the result must be non-empty printable ASCII, else refused. Fullwidth and ligature forms fold to the same person; homoglyphs from other scripts are refused. The stored form is the normalised form and SQL CHECKs reject anything else (lower-case printable ASCII, single spaces), so UNIQUE and the self-approval trigger operate on the normalised value even for direct inserts, and `approvers()` re-normalises and excludes the requester. Cost: non-ASCII names are not accepted as identities; fine for operator names, to be revisited with real authentication.
- `lock_proof.py`: the Tier 2 holder-death proof. The lock id is parsed from the failed step's log (exactly one id, ANSI stripped). The lock table entry names the holder's execution id; the proof holds only if that execution exists in the execution source with a terminal status AND the table does not mark it alive. A running holder (either source) is `running` (the gate's hard refusal); anything missing, ambiguous or unfamiliar is `unknown` (the gate downgrades). Nothing in it comes from the model.
- `approval_flow.py`: `ApprovalService` (approve / deny / expire-check, each audited, refusals included; it now requires the orchestrator so approving can run the gate) and `execute_approved`. Both use one `_evaluate` (stage `approval_precheck` at approve time, `approval_recheck` at execute time). Execution order: status and expiry check, then the gate is re-run from fresh facts, then the stubbed dry run, then an atomic claim (`approved -> executed`, so a request runs once even with two processes), then the stubbed execute, then the stubbed verify. A gate refusal or downgrade cancels the request. Tier, action and execution id come from the immutable request row, never from the stored payload.
- `orchestrator.py` (additive, all optional): `approvals`, `triggered_by`, `locks`, `gate_factory`. A Tier 1/2 proposal that passes the gate and the target's dry run opens a pending request and stops at `AWAITING_APPROVAL`. Without a store nothing changes from MVP 1. Tier 2 facts now come from `lock_proof` (lock id from the log, never from `proposal.params`); the model-supplied `lock_id` is ignored and overwritten.
- `approvals_cli.py` and `python tasks.py approvals <list|show|approve|deny|expire-check|execute>`. `approve` and `deny` need `--as <identity>` (no default). Every command prints that it is synthetic-target-only and unauthenticated. `tasks.py` accepts extra arguments for `approvals` only and injects none; `approvals` left `NOT_IMPLEMENTED`; `eval-tier12` was added.
- `eval/tier12_cases.py` and `python tasks.py eval-tier12`: the eval section (below).
- Small supporting changes: `RateLimiter.seed`, `record_decision(**extra)`, `LockTable.to_json/from_json` + `load_lock_table/save_lock_table`, the synthetic target also accepts the catalog's `force_unlock_state` name, `make_synthetic_target(lock_table=...)`.

## Why

- **An approval is one input, not an authorisation.** The gate is re-run at execution with fresh facts (kill switch re-read from disk, abort ceiling from policy, blast radius from the source, rate limit seeded from the audit log, Tier 2 proof re-derived from the lock table). Only `allowed` continues. The gate can only downgrade, so an approval can neither raise a tier nor turn a refused or downgraded decision into allowed: a request created by hand for a fleet-wide Tier 1, or for a Tier 2 with no proof, is cancelled at execution even with every approval in place.
- **The dry run before the gate is a plan, not a target call.** SafetyGate needs `dry_run_ok` for Tier 2, but invariant 1 forbids reaching the target before the gate. `dry_run_ok` is therefore the deterministic unlock plan (lock found, holder identified and dead). The target's own dry run happens after the gate allows, as for Tier 0.
- **Rate limit across processes.** The gate's limiter is in memory, so a CLI process would start empty. At execution the limiter is seeded from the audit log: earlier allowed attempts for the fingerprint within the hour, excluding this request's own request-time decision and execution-time re-checks (audited with `stage: approval_recheck`, which are not attempts). Executing therefore counts as the next attempt in the current window: with two other attempts in the hour it is refused.
- **Outcome vocabulary.** The orchestrator already had `awaiting_approval`; it is kept. A Tier 1/2 that passes the gate is "awaiting approval", never executed without approvals; the `Report` contract has no outcome field, so no contract change was needed. Final states reuse the existing vocabulary: `executed`, or `escalated` for expired, denied, cancelled and refused.
- **Audit vocabulary.** The KINDS pin holds. Everything is an existing kind plus a `stage`: `proposal/approval_requested`, `proposal/approval_decision`, `proposal/holder_proof`, `rejected/approval_refused`, `rejected/approval_denied`, `expired/approval`, `gate_decision/approval_recheck`, `rejected/approval_execute_refused`, then `execution` (`dry_run`, `execute`), `verification` (`result`, `closed`) and `failed`, each carrying `request_id`.

## CLI trust model (round 2)

The inputs that decide whether an approved action may run are PINNED and no command-line flag can change them: the kill switch (`config/kill_switch.json`), the policy and abort ceiling (`config/policy.json`), the audit log that seeds the rate limit (`state/audit.jsonl`), the simulated lock table (`state/locks.json`) and the dataset (`data/`). The flags `--data`, `--kill-switch`, `--policy`, `--audit` and `--locks` were removed; argparse rejects unknown options loudly (abbreviations are disabled too, so `--kill` is an error, not a near match), and `tasks.py approvals` forwards exactly what the operator typed and injects nothing, so nothing can be overridden by a later flag. The only path left is `--state-dir`, and it selects only where `approvals.sqlite` lives (a demo may keep a separate approvals database). Tests inject paths through `CliInputs`, a keyword argument of `main()` (library API, not reachable from a command line). Identities remain unauthenticated: whoever can run the CLI can type any name, and whoever can write the approvals file can forge decisions; the controls are bookkeeping plus the fresh gate at execution, which a forged approval cannot get past.

## Identities are NOT authentication

The CLI takes a name from `--as`. Nothing proves who typed it. That is acceptable for MVP 2 because the CLI is a trusted local operator interface on the machine that owns the state directory, the target is simulated, and the controls here are bookkeeping against accidents: the same person counting twice, the trigger approving their own run, a stale or reopened request. They do not stop someone with shell access from typing two names. Anything beyond a local simulation needs real identity first: Slack (the planned next step) would bring a verified user id per approval, and the store would key on that instead of a typed string; the same-person, self-approval and quorum rules carry over unchanged because they are about identity equality, not about how identity is established. Until then, do not describe approvals as two-person control; describe them as a recorded two-name quorum.

## Eval

`python tasks.py eval-tier12` prints a separate, clearly labelled section; the main `eval` table and the dataset are untouched (the generator was not modified; regenerating gives 851/851 identical files).

- The 8 labelled Tier 1/2 scenarios (4 each), driven with the label's own proposal. Expected, from the PRD rules and not from a run: Tier 1 on a single resource is allowed and executes after one approval (sc-10, sc-12); Tier 1 on a fleet-wide incident is downgraded by the abort ceiling (sc-09, sc-16); Tier 2 is downgraded in all four (sc-03, sc-11, sc-29, sc-33) because the dataset records no lock holder, so there is no proof to be had. All 8 match. The labels say `escalate` for all of them, which was the MVP 1 reading (nothing could execute); the gate-level expectation is finer and is what is checked here.
- 23 dedicated cases the 33 scenarios cannot express, on a simulated lock table plus an overlay of holder executions: approve once, 14:59 and exactly 15:00, approved but late, self-approval (and spelling), deny, kill switch (per tier and global) after approval, two approvers with a dead holder, confidence ignored with proof, live holder, table-alive-only, one approver, the same person twice, trigger as second approver, holder live after approval, Tier 2 timeout, denial after approval, high confidence with no lock in the table, holder execution unknown, non-terminal holder status. 31/31 match.

## Open doubts

1. **Tier 2 has no timeout in the PRD.** I used 60 minutes (`TIER2_TIMEOUT_S`) rather than an unbounded window. Needs a decision.
2. **The dataset cannot express a provable holder.** No generated execution records which execution holds a lock, so in the 33 scenarios Tier 2 can only ever be downgraded; the allowed path exists only on the simulated lock table of the dedicated cases. I did not change the generator (it would invalidate the frozen MVP 1 fixtures). The convention `LockEntry.holder = holder's execution id` is mine.
3. **Who triggered a run** has no field in the dataset. The orchestrator takes a `triggered_by` resolver; if it is missing or returns nothing, no request is opened (escalation), because self-approval could not be prevented. The CLI cannot create requests; they come from orchestrator runs (library or tests). A demo seeding command was out of scope.
4. **Approvals pass through SafetyGate (decided by the human, round 2).** `approve` runs the gate from fresh facts and refuses early (`GateRefused`) when the gate would not allow the action now (kill switch off, abort ceiling, Tier 2 holder alive or unproven, rate limit). An early refusal is audited (`gate_decision/approval_precheck`, `rejected/approval_refused`) and changes nothing else: no decision is recorded and the request stays pending, not cancelled, because the condition may be temporary and the request expires on its own window anyway; `execute` re-runs the full gate regardless and is what cancels. `deny` is exempt (denial is the safe direction; the requester may deny their own request). The result of the precheck is only ever used to say no, so an approval cannot raise a tier or flip refused/downgraded to allowed.
5. **The requester may deny their own request** (conservative, allowed; confirmed in round 2). A person can decide once per request, so approve-then-deny by the same person is refused as a repeat decision.
6. **No re-investigation or attempt record after an approved execution.** The Tier 0 verification loop (rollback, one re-investigation) is not applied; a failed verification of an approved action is recorded in the audit log and the request note and the case escalates, but the in-memory attempt store is not updated and nothing is rolled back. Tier 2 is irreversible by definition.
7. **Request-time rate limit is still per-process memory** (unchanged from M4); only the execution-time check is seeded from the audit log.
8. **Concurrency** relies on SQLite `BEGIN IMMEDIATE` and the atomic claim; there is no multi-process stress test.
9. The scripted-model double used by the eval proposes a fixed `lock_id` of `model-invented-lock` on purpose, to show the orchestrator ignores it. That is a test-double value, not error text.

## Round 2 notes

- Expiry found by the claim (the window closing between the gate/dry run and the claim) now writes the same `expired/approval` audit entry as the other paths; before, the claim had already recorded the expiry so `expire_due()` found nothing to audit.
- `derive_holder_proof` takes the failing execution id: a lock whose holder is the failing execution itself is contradictory and yields `unknown` (a downgrade), never `dead`.
- `dry_run_ok` on the Tier 2 gate facts is kept (redundant behind the proof check, unchanged); new tests cover a proven holder whose target dry run then fails (Tier 1 and Tier 2): never executes, audited, request cancelled.
- `ApprovalService` now needs `orchestrator=`; two existing tests that forced requests the gate would refuse now write their approvals through the store directly (the point of those tests is that `execute` re-checks anyway; assertions unchanged).

## Hardening

Follow-up to the round 2 review (non-blocking findings F1, F2, F3, F5 fixed; F4 and F6 accepted, see BLOCKERS.md).

- **Schema version (F1).** `PRAGMA user_version` is set to `SCHEMA_VERSION` when a database is created, in the same transaction as the schema. Opening an existing file requires the right version AND that its tables, indexes and triggers (names and SQL) equal the current schema, otherwise `SchemaError` is raised and the file is left untouched. Stale-DB behaviour: a `state/approvals.sqlite` from an earlier build (no version, or old tables without the CHECKs and triggers) is REFUSED, never migrated and never run with the old rules; the CLI prints `refused: ...` and exits 1. There is no migration: archive the old file (its history is evidence), remove it so a fresh one is created, and rerun. `SCHEMA_VERSION` must be bumped with any change to the schema text; the signature comparison also catches a forgotten bump.
- **Backstops tested without triggers (F2).** Tests drop every trigger and ignore CHECKs, then forge decisions and statuses directly. `claim_for_execution`, `approvers()` and the recount at the top of `execute_approved` each still refuse one approver, the requester, duplicate spellings and unnormalisable names for Tier 2 and under-quorum Tier 1.
- **Embedded NUL (F3).** Checked against the real sqlite3 (3.45.3 here): `length()` and `GLOB` stop at an embedded NUL (`length('alice\0a')` is 5, the printable-ASCII GLOB passes), while `instr(x, char(0))` and `length(CAST(x AS BLOB))` see it. The identity CHECKs on `requests.requested_by` and `decisions.approver` now also require `instr(x, char(0)) = 0` and `length(x) = length(CAST(x AS BLOB))`. `normalize_identity` already refused NUL (category Cc); tests cover both layers, including a NUL variant of the requester.
- **CLI load errors (F5).** The gate-input load catch now includes `AttributeError` (a locks file holding a list, number, null or string); a non-object file prints `refused: the gate inputs could not be loaded` and exits 1. A malformed policy or kill-switch file is not a load error: the gate already fails closed on it (strictest abort ceiling, switch off). A malformed schema is reported the same way.
- **`approvals show` (operator visibility).** Lists the request's audit history (every entry carrying its `request_id`, plus the request-time gate decision): sequence, time, kind, stage, decision, approver, error and the gate's short reason, so a request stuck pending (`approval_precheck` refused, `approval_refused`) can be told from one that timed out (`expired`).
