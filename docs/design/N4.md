# N4: Tier 1/2 with persisted CLI approvals

Branch `mvp2/n4-approvals`. Tier 1 and Tier 2 actions stay stubbed: the only target is the synthetic one, nothing runs against live infrastructure, and the GitHub adapter gained nothing.

## What was built

- `approvals.py`: the SQLite store (stdlib `sqlite3`) at `state/approvals.sqlite` (outside `data/`, which `tasks.py data` regenerates; `state/` is gitignored; the path and the clock are injected). Tables `requests` (id, execution_id, fingerprint, tier, action, requested_by, requested_at, expires_at, status, required, payload, note, gate_seq) and `decisions` (request_id, approver, decision approve|deny, at). Statuses: `pending -> approved | denied | expired | cancelled`, `approved -> executed | expired | cancelled`; the rest are terminal.
  - Tier 1: one approval, 15 minutes (`TIER1_TIMEOUT_S`). Tier 2: two approvals from two different people. A request is expired when `now >= expires_at`, so an approval at exactly 15:00 is refused; one at 14:59.999 is accepted. Expiry covers `approved` requests that were not executed in time, so an approval does not outlive its window.
  - Rules enforced in code AND in SQLite: `UNIQUE(request_id, approver)`; a trigger refuses an approval by the person who triggered the run; a trigger refuses decisions on a request that is not pending; a trigger allows only forward status transitions and freezes tier/action/execution/requester; decisions are append-only. Any denial ends the request (fail closed).
  - Identities are normalised (NFKC, whitespace collapsed, case-folded) so `Alice`, ` ALICE ` and `alice` are one person. An empty identity is refused everywhere.
- `lock_proof.py`: the Tier 2 holder-death proof. The lock id is parsed from the failed step's log (exactly one id, ANSI stripped). The lock table entry names the holder's execution id; the proof holds only if that execution exists in the execution source with a terminal status AND the table does not mark it alive. A running holder (either source) is `running` (the gate's hard refusal); anything missing, ambiguous or unfamiliar is `unknown` (the gate downgrades). Nothing in it comes from the model.
- `approval_flow.py`: `ApprovalService` (approve / deny / expire-check, each audited, refusals included) and `execute_approved`. Execution order: status and expiry check, then the gate is re-run from fresh facts, then the stubbed dry run, then an atomic claim (`approved -> executed`, so a request runs once even with two processes), then the stubbed execute, then the stubbed verify. A gate refusal or downgrade cancels the request. Tier, action and execution id come from the immutable request row, never from the stored payload.
- `orchestrator.py` (additive, all optional): `approvals`, `triggered_by`, `locks`, `gate_factory`. A Tier 1/2 proposal that passes the gate and the target's dry run opens a pending request and stops at `AWAITING_APPROVAL`. Without a store nothing changes from MVP 1. Tier 2 facts now come from `lock_proof` (lock id from the log, never from `proposal.params`); the model-supplied `lock_id` is ignored and overwritten.
- `approvals_cli.py` and `python tasks.py approvals <list|show|approve|deny|expire-check|execute>`. `approve` and `deny` need `--as <identity>` (no default). Every command prints that it is synthetic-target-only and unauthenticated. `tasks.py` accepts extra arguments for `approvals` only; `approvals` left `NOT_IMPLEMENTED`; `eval-tier12` was added.
- `eval/tier12_cases.py` and `python tasks.py eval-tier12`: the eval section (below).
- Small supporting changes: `RateLimiter.seed`, `record_decision(**extra)`, `LockTable.to_json/from_json` + `load_lock_table/save_lock_table`, the synthetic target also accepts the catalog's `force_unlock_state` name, `make_synthetic_target(lock_table=...)`.

## Why

- **An approval is one input, not an authorisation.** The gate is re-run at execution with fresh facts (kill switch re-read from disk, abort ceiling from policy, blast radius from the source, rate limit seeded from the audit log, Tier 2 proof re-derived from the lock table). Only `allowed` continues. The gate can only downgrade, so an approval can neither raise a tier nor turn a refused or downgraded decision into allowed: a request created by hand for a fleet-wide Tier 1, or for a Tier 2 with no proof, is cancelled at execution even with every approval in place.
- **The dry run before the gate is a plan, not a target call.** SafetyGate needs `dry_run_ok` for Tier 2, but invariant 1 forbids reaching the target before the gate. `dry_run_ok` is therefore the deterministic unlock plan (lock found, holder identified and dead). The target's own dry run happens after the gate allows, as for Tier 0.
- **Rate limit across processes.** The gate's limiter is in memory, so a CLI process would start empty. At execution the limiter is seeded from the audit log: earlier allowed attempts for the fingerprint within the hour, excluding this request's own request-time decision and execution-time re-checks (audited with `stage: approval_recheck`, which are not attempts). Executing therefore counts as the next attempt in the current window: with two other attempts in the hour it is refused.
- **Outcome vocabulary.** The orchestrator already had `awaiting_approval`; it is kept. A Tier 1/2 that passes the gate is "awaiting approval", never executed without approvals; the `Report` contract has no outcome field, so no contract change was needed. Final states reuse the existing vocabulary: `executed`, or `escalated` for expired, denied, cancelled and refused.
- **Audit vocabulary.** The KINDS pin holds. Everything is an existing kind plus a `stage`: `proposal/approval_requested`, `proposal/approval_decision`, `proposal/holder_proof`, `rejected/approval_refused`, `rejected/approval_denied`, `expired/approval`, `gate_decision/approval_recheck`, `rejected/approval_execute_refused`, then `execution` (`dry_run`, `execute`), `verification` (`result`, `closed`) and `failed`, each carrying `request_id`.

## Identities are NOT authentication

The CLI takes a name from `--as`. Nothing proves who typed it. That is acceptable for MVP 2 because the CLI is a trusted local operator interface on the machine that owns the state directory, the target is simulated, and the controls here are bookkeeping against accidents: the same person counting twice, the trigger approving their own run, a stale or reopened request. They do not stop someone with shell access from typing two names. Anything beyond a local simulation needs real identity first: Slack (the planned next step) would bring a verified user id per approval, and the store would key on that instead of a typed string; the same-person, self-approval and quorum rules carry over unchanged because they are about identity equality, not about how identity is established. Until then, do not describe approvals as two-person control; describe them as a recorded two-name quorum.

## Tested

`tests/approvals` (plus `tests/github/test_gh_tier12.py`). Offline, fake clock, no sleep, network blocked by the autouse fixture.

- Store: 15:00 boundary (just before, exactly at, after), expired/denied requests cannot be approved or claimed (also with the clock rewound), same person under spelling variants, empty identities, `UNIQUE` hit by a direct insert, self-approval by code and by direct insert, forward-only transitions and append-only decisions by direct SQL, atomic claim, one open request per execution/action, pending requests and decisions surviving close/reopen.
- Flow: timeout escalates (audited), live holder refused, one approver refused, self-approval refused (Tier 1 and 2), model confidence ignored in both directions (with and without proof), model-chosen lock id ignored, kill switch (global, per tier, malformed file) flipped after approval, holder going live or vanishing after approval, abort ceiling and missing proof not overridable by approvals, rate limit at execution (two others refuse, one other and old ones pass, rechecks are not attempts), denied/executed requests never run, full audit trail, restart then approve then execute.
- Properties (seeded, 24 runs): random interleavings of approve/deny/advance/kill switch/holder flips/execute; an action is executed only if, at that moment, enough distinct non-trigger approvals exist, none denied, the window is open, the switch is on and (Tier 2) the holder is dead; at most once. The gate on the approval path never ranks below the incoming decision and never changes the tier; a payload claiming another tier changes nothing.
- Architecture: agents/ and tools/ import nothing approval-related; only the wiring modules import the store; the GitHub adapter has no Tier 1/2 or lock code and its target refuses Tier 1/2 with zero HTTP calls even when "allowed"; the GitHub orchestrator builder cannot be given a store; new modules have no sleep, network or env access.
- Mutation spot check (12 mutations: boundary operator, self-approval code and trigger, UNIQUE, Tier 2 quorum, skipped recheck, rate-limit seeding, table-alive, non-terminal status, running-holder refusal): all fail the suite except one equivalent mutant (`dry_run_ok`, redundant behind the gate's own proof check).
- CLI: in-process with a manual clock; `--as` required, trust-model banner and help, list/show, Tier 1 and Tier 2 end to end, expire-check, kill switch, live holder in the lock file.

## Eval

`python tasks.py eval-tier12` prints a separate, clearly labelled section; the main `eval` table and the dataset are untouched (the generator was not modified; regenerating gives 851/851 identical files).

- The 8 labelled Tier 1/2 scenarios (4 each), driven with the label's own proposal. Expected, from the PRD rules and not from a run: Tier 1 on a single resource is allowed and executes after one approval (sc-10, sc-12); Tier 1 on a fleet-wide incident is downgraded by the abort ceiling (sc-09, sc-16); Tier 2 is downgraded in all four (sc-03, sc-11, sc-29, sc-33) because the dataset records no lock holder, so there is no proof to be had. All 8 match. The labels say `escalate` for all of them, which was the MVP 1 reading (nothing could execute); the gate-level expectation is finer and is what is checked here.
- 23 dedicated cases the 33 scenarios cannot express, on a simulated lock table plus an overlay of holder executions: approve once, 14:59 and exactly 15:00, approved but late, self-approval (and spelling), deny, kill switch (per tier and global) after approval, two approvers with a dead holder, confidence ignored with proof, live holder, table-alive-only, one approver, the same person twice, trigger as second approver, holder live after approval, Tier 2 timeout, denial after approval, high confidence with no lock in the table, holder execution unknown, non-terminal holder status. 31/31 match.

## Open doubts

1. **Tier 2 has no timeout in the PRD.** I used 60 minutes (`TIER2_TIMEOUT_S`) rather than an unbounded window. Needs a decision.
2. **The dataset cannot express a provable holder.** No generated execution records which execution holds a lock, so in the 33 scenarios Tier 2 can only ever be downgraded; the allowed path exists only on the simulated lock table of the dedicated cases. I did not change the generator (it would invalidate the frozen MVP 1 fixtures). The convention `LockEntry.holder = holder's execution id` is mine.
3. **Who triggered a run** has no field in the dataset. The orchestrator takes a `triggered_by` resolver; if it is missing or returns nothing, no request is opened (escalation), because self-approval could not be prevented. The CLI cannot create requests; they come from orchestrator runs (library or tests). A demo seeding command was out of scope.
4. **Approvals are not gate decisions at approval time.** Only execution is gated (that is where effects happen). An operator can approve while a kill switch is off and learns at `execute`. Say if approve-time pre-checks are wanted.
5. **The requester may deny their own request** (conservative, allowed). A person can decide once per request, so approve-then-deny by the same person is refused as a repeat decision.
6. **No re-investigation or attempt record after an approved execution.** The Tier 0 verification loop (rollback, one re-investigation) is not applied; a failed verification of an approved action is recorded in the audit log and the request note and the case escalates, but the in-memory attempt store is not updated and nothing is rolled back. Tier 2 is irreversible by definition.
7. **Request-time rate limit is still per-process memory** (unchanged from M4); only the execution-time check is seeded from the audit log.
8. **Concurrency** relies on SQLite `BEGIN IMMEDIATE` and the atomic claim; there is no multi-process stress test.
9. The scripted-model double used by the eval proposes a fixed `lock_id` of `model-invented-lock` on purpose, to show the orchestrator ignores it. That is a test-double value, not error text.
